# Command Contracts

Canonical writes are submitted to the gateway; direct writes from models, projections, importers, or UI components are prohibited.

## Envelope

```json
{
  "workspace_id": "workspace_001",
  "branch_id": "main",
  "command_type": "create_entity",
  "expected_revision": 4,
  "idempotency_key": "request-unique-id",
  "actor": "user",
  "reason": "Add a character from reviewed source material",
  "payload": {"entity_id": "aria", "entity_type": "character", "label": "Aria", "properties": {}}
}
```

## Invariants

1. Validate workspace and branch existence and scope before mutation.
2. Reject stale `expected_revision`; never silently rebase a command.
3. The same idempotency key and same envelope returns its recorded result without a second write. Reuse with different input is a conflict.
4. Validate references inside the same workspace and branch. Relations and claims cannot point to records in another scope.
5. AI actors may propose claims, relations, rules, scenario assumptions, and extraction candidates but cannot accept or review them. They cannot create a scenario frame directly.
6. Evidence quotes must match the preserved source content.
7. A successful mutation increments the branch head once and writes the domain row, revision, audit event, projection outbox item, and idempotency result in one transaction.
8. Duplicate source content is a no-op and does not create a second source or revision.
9. Audit events are append-only. Real personal-data deletion needs a separate documented privacy operation; it cannot be implemented by rewriting audit history.
10. Derived projections can be rebuilt from canonical content and recorded commands.

## Implemented command set

`create_entity`, `update_entity`, `add_relation`, `update_relation`, `review_relation`, `add_claim`, `update_claim`, `review_claim`, `add_belief`, `import_source`, `add_evidence`, `create_conversation`, `append_story_turn`, `create_story_world`, `revise_story_world`, `import_story_world`, `duplicate_story_world`, `set_story_world_archived`, `create_story_adventure`, `set_story_adventure_library_state`, `import_story_adventure`, `update_rpg_sheet`, `record_d20_check`, `record_rpg_mechanic_check`, `update_story_skills`, `award_story_experience`, `set_story_ability_active`, `propose_rpg_state`, `review_rpg_state_proposal`, `create_story_memory`, `revise_story_memory`, `review_story_memory`, `save_story_thread`, `update_story_npc`, `create_story_npc`, `travel_to_location`, `add_story_asset`, `set_npc_simulation`, `create_journal_event`, `revise_journal_event`, `create_rule`, `review_rule`, `create_scenario`, `set_scenario_assumption`, `review_scenario_assumption`, `record_extraction_batch`, `review_extraction_candidate`, `import_exchange`, and `promote_branch` are implemented on schema v17. `create_story_npc` creates a character identity and adventure profile in one transaction. `import_exchange` stores an immutable branch-local transcript segment, detects gaps across turn 1 through the latest declared transcript total, rejects conflicting overlaps within its stable transcript ID, and does not write story turns or canonical facts. `create_branch` creates a revision-bound snapshot of canonical records, story history, adventures and their RPG state, external exchanges, rules, journal-event versions, scenario options, evidence links, assumption versions, and extraction batches/candidates with its own audit/outbox record.

The `/sources/{source_id}/extract` route sends a selected local model a bounded text source and records schema-validated entity/claim candidates through `record_extraction_batch`. Each candidate must include a quote matching its exact source span. The batch records source digest and model/prompt/schema versions; idempotent retries replay the saved batch without rerunning the model. `review_extraction_candidate` can reject a candidate or accept an entity/claim with its exact source evidence in one transaction. Accepting a claim requires a user-selected subject entity, epistemic status, and visibility. Candidate payloads are immutable, and AI actors cannot review them.

`update_entity`, `update_relation`, and `update_claim` provide human corrections to records in the selected branch. They return before/after values in the audit result and revision history; AI actors cannot execute them. Entity corrections preserve the stable entity ID. Correcting a reviewed relationship or claim returns it to proposed status so the changed record must be reviewed again. Claim evidence can be replaced only with evidence records present in that same workspace branch. An unchanged correction creates no new revision.

Re-running extraction records new proposed candidates and does not overwrite an accepted or manually corrected canonical claim. Independently accepted duplicate claims across batches are not deduplicated yet.

`append_story_turn` writes the user's prompt and local-model response in one command, recording provider, model, narrative order, context manifest, and context revision. Generated text is conversation history, not an accepted fact or state change. Its retry fingerprint excludes nondeterministic model output and the per-request manifest ID while binding the workspace, branch, prompt, model, order, and expected revision.

`create_story_world` creates the first workspace world version on `main`; `revise_story_world` appends a new immutable version after an expected-version check. World content is size-bounded JSON and rejects secret-like field names. An optional `cover_image` stores a small validated local image with alt text in the immutable world version. An optional `character_creation` contract defines a point budget, unspent/below-baseline options, and per-stat labels, bounds, and point costs against the world's baseline `stats`; trackers remain separate. An optional `game_mechanics` profile defines d20/custom-dice/narrative-only/hybrid resolution, difficulty and encounter lists, skills, and experience rules. Both world commands validate these contracts, and package exports preserve them. Neither command can be executed by an AI actor. `duplicate_story_world` copies a world's version history to a new identity. `set_story_world_archived` records or clears the world's archive timestamp without deleting history. `create_story_adventure` is allowed only in a new direct-child snapshot of `main`, requires a character from that snapshot, pins an existing non-archived world version, and initializes its character sheet from the pinned template. When that world has point-buy rules, the command validates the submitted `stats` against the pinned version and creation budget before writing the sheet; the API preflights allocation before creating the branch. World changes do not propagate to existing adventures. `set_story_adventure_library_state` updates the adventure name, active/paused/complete status, or archive timestamp through a revisioned command. The authenticated API exposes world and adventure libraries, version creation, adventure start/resume, RPG state, d20 checks and configured mechanics checks.

`update_rpg_sheet` lets the user adjust bounded stat modifiers and trackers or the adventure's current location. `record_d20_check` stores a die result from 1 to 20 and calculates `total = die_roll + current stat modifier` and success against the supplied visible target; the provider does not calculate or change this result. For worlds with an explicit mechanics profile, `record_rpg_mechanic_check` validates rolls against the pinned dice, encounter, difficulty, stat, and skill rules, then records the full rule snapshot with the deterministic result. The authenticated API generates configured dice and replays an idempotent request without rerolling. `update_story_skills` changes ranks only within the pinned definitions; `award_story_experience` is player-only, requires a manual-award rule, and validates the remaining XP cap. Automatic XP is derived from completed player turns. AI actors cannot roll checks, change skills, award XP, or edit sheets. `propose_rpg_state` records a proposed tracker delta or location change, optionally linked to an assistant turn; a proposal is not part of the model context or canonical sheet while pending. `review_rpg_state_proposal` is human-only. Acceptance validates tracker limits and rejects stale branch revisions or proposals whose sheet changed after creation. Rejection records the decision without changing the sheet. All sheet, skill, XP and check writes use the normal revision, audit, outbox, and idempotency transaction.

World versions may define exceptional abilities with a stable ID, name, description, category/source, activation/deactivation, effects, explicitly declared resource costs and completed-turn cooldowns, duration/range, interaction with ordinary magic, demonstrated capabilities, confirmed limitations, and unresolved aspects. `create_story_adventure` pins those definitions and starts a separate inactive state for each ability; package import/export and branch snapshots preserve the state. `set_story_ability_active` is player-only and requires an ability ID from the pinned world version. It charges only explicitly declared tracker costs when activating and enforces only an explicitly declared cooldown. A null/absent cost or cooldown adds no rule. Activation does not perform or require a d20 check, and no level or mana restriction is inferred. Each state mutation is revisioned, audited, idempotent, and reconstructed from canonical history.

`create_journal_event` records a user-provided account with participants, exact/range/relative/unknown timing, and optional workspace source plus an exact quote. It does not assert that the account is verified. `revise_journal_event` requires the current event version and appends a correction; it cannot overwrite earlier wording. Separate event IDs remain separate when accounts conflict. AI actors cannot create or revise personal accounts.

`create_rule` records a proposed require/forbid condition on one entity, predicate, and value; `review_rule` is required before evaluation is active. The deterministic evaluator uses accepted public claims marked `known`. Unknown or private data never proves a rule, and conflicting values for an explicitly single-valued predicate return unknown. AI actors cannot accept rules. Rule evaluations are read-only projections and do not mutate canonical state.

`create_scenario` records a decision problem, constraints, two or three named options, and links to branch claims or workspace sources. `set_scenario_assumption` creates or revises an append-only assumption version for one option. Revisions require the latest assumption version; AI-originated assumptions remain proposed until a user reviews them. `replace` is valid only for a declared single-valued property, while `add` is valid only for a multi-valued property. `review_scenario_assumption` appends an accepted or rejected version and rejects stale reviews. The scenario evaluation read model applies accepted assumptions only to their option, reports deterministic rule outcomes as conditional, and preserves separate claim and assumption references. It never writes assumptions into canonical claims or predicts or scores outcomes.

`promote_branch` is an explicit fast-forward from a direct child into its parent. The request names the exact source head revision and uses the parent's current expected revision. Promotion is allowed only when the parent still equals the child's recorded starting revision and the child contains changes. AI actors cannot promote. The gateway copies the branch-scoped canonical snapshot in dependency order, remaps child-created or updated revision markers to the single parent promotion revision, rebuilds the parent entity-search projection, and writes one parent revision, audit event, outbox item, and idempotency result in the same transaction. Immutable journal, scenario, evidence, and extraction history is inserted without rewriting existing parent history. The child and its revision history remain intact; the audit payload identifies the source branch and promoted revision range. There is no automatic conflict merge.

`import_story_world` validates a bounded `lke.world.v2` package (or fully validates and upcasts the exact v1 schema), requires a new world ID, and atomically copies its contiguous version sequence into the main-branch library. The package manifest checks the canonical JSON payload with SHA-256; adventure packages also checksum each decoded image. The audit command records the package and source workspace/world IDs; imported versions receive the destination revision. World packages may contain private notes and are duplicate-only. Adventure package preview/import validates the pinned world, remaps conflicting character IDs, and creates an isolated branch snapshot with turns, memories, NPCs, map locations, local assets and RPG state. Context manifests are omitted. Package v1-to-v2 migration rules are defined in `PORTABLE_PACKAGES.md`; unknown versions are rejected. MNO preview routes convert supported `.mno-world` v1 and `.mno-adv` v2 exports into these packages; matching MNO worlds are required before adventure preview. MNO formulas are preserved but never executed, imported role metadata excludes thoughts/meta from later prompts, and the adventure source archive is size-bounded and immutable. Credential-like keys are rejected. Review imported content before sharing; provider settings are never imported.

Every committed adventure turn and every edit or retry of an assistant scene creates a sourced, actor-scoped event-memory proposal in the same command transaction. The proposal contains a bounded scene excerpt and requires human review; it never becomes canon automatically. Editing or removing the source turn makes its pending review stale and retrieval excludes its accepted record until a revised proposal is reviewed. This is a sourced excerpt workflow, not semantic event extraction.

Editing or hiding any transcript turn automatically supersedes every later stored turn in that conversation, based on canonical `turn_order`. The client cannot leave a later response active by omitting downstream IDs. Earlier turn versions remain in immutable edit history, and the edited turn can be regenerated from its preceding active player direction.

Story-turn edits, memory review, NPC profiles, map locations, travel, local image attachments, and opt-in NPC simulation also have gateway commands. MNO world-cast additions create the identity and profile atomically; attaching a portrait is a separate asset command. Historical state reconstruction after edits, semantic event/correction links, generalized merge, authored map editing, and generated/selectively revised publishing workflows remain incomplete; consult the acceptance matrix for current evidence.

## Failure behavior

Malformed payload: validation error, no write. Missing scoped record: not found, no write. Stale revision or duplicate identity: conflict, no write. Provider failure: no command is submitted unless a proposal exists; no partial canonical commit. Database failure before commit: rollback. Retrying a committed request with the original key: replay its original result.
